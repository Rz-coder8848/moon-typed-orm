## 1. 项目价值与生态定位

mooncakes.io 上数据库这块我翻过：`moonorm`（SQLAlchemy 式，带 Session、模型、迁移）和它底下的 `moondb` 已经成熟，但它走运行时模型，列名、类型写错要到跑起来才炸——编译期这层保护，MoonBit 生态里现在是空的，我补的就是这个位。

手写 SQL 两个老毛病：字符串拼 SQL，用户输入直接拼进去就是注入；列名类型写错，编译器一个字不吭，上线才报。MoonBit 的静态类型正好治这个。所以查询做成带类型的列 DSL：`Column[Int]` 只能跟 `Int` 比，传 `String` 编译直接不过；所有值一律转 `?` 占位符 + 参数数组，值根本拼不进 SQL 字符串。跟 `moonorm` 不是「再写一个 ORM」，是两条路：它管模型和 Session，我管编译期把 SQL 拼对；它默认连真库，我内置零依赖内存后端，wasm-gc 就能跑，测试不用起库。

## 2. 交付范围与工程边界

做出来的是：`Select`/`Insert`/`Update`/`Delete` 四个构建器，渲染成 `{ sql, params }`；条件 DSL 全套（比较、`in_`、`is_null`、`and_`/`or_`/`not_`，留一个 `raw` 逃生口）；聚合 + `group_by`/`having`；四种 JOIN；子查询 `IN`/`EXISTS`/标量比较，相关子查询单层。两个后端走同一个 `Connection` trait，事务是可选 trait。测试 48 个 wasm-gc 用例 + 3 个 native 用例全绿，渲染用例把 SQL 文本和参数顺序钉死，`cmd/demo` 一条命令跑完整个功能面。

明确不做：Postgres 驱动、migration/schema 管理、多层相关子查询。不是不会，是现在不做——查询构建器就该是个聚焦的小库，摊大饼反而做不完。现在 2100 行有效代码 + 1000 行测试，这个体量是它该有的样子。

## 3. 实现路径与技术理解

做查询构建器两条路：宏把 SQL 嵌进代码（sqlx 那种），或者运行时 DSL + phantom type 把类型带进列（Diesel、Slick 那种）。MoonBit 的宏生态还没起来，第一条走不通，我走第二条——`Column[Int]` 这种 phantom type 把列类型带进 DSL，类型错配编译期就拦。这条路别的语言走过，MoonBit 里还没人做，这是我选的位。

真正磨人的不是语法，是 MoonBit 的接口规则，全是编译报错一行行逼出来的：`pub enum` 变体包外只读，逼出 `Value::int()` 智能构造函数；`pub trait` 包外实现不了，得 `pub(open)` 才能让 SQLite 后端跨包实现 `Connection`；`and`/`or`/`not` 是关键字，方法只能叫 `and_`/`or_`/`not_`。包名带连字符 `moon-typed-orm` 连 `@` 缩写都写不出来，黑盒测试只好改白盒。这些坑记在仓库「开发历程」里，是真实记录。
