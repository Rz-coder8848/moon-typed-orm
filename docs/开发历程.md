# MoonORM 开发历程

## 选题

MoonBit 生态里，数据库访问这一层还是空缺的。查了一圈 mooncakes.io，有几个
零散的数据库绑定，但没有一个把「类型安全」和「查询构建」做起来的 ORM。而
SQL 拼接是注入风险的重灾区——MoonBit 的静态类型正好适合把列和值都钉死类型，
在编译期挡住大部分手滑。

所以做 MoonORM：一个类型安全、参数化的 SQL 查询构建器，加一个可替换的
连接边界和一个零依赖的内存后端。

## 工程任务单（照这个顺序推进）

1. **确认目标与约束**
   - 目标：类型安全的查询构建器 + 可替换后端 + 一个能跑起来的 demo。
   - 约束：本机没有 C 编译器，只能走 wasm-gc 目标；除 core 外零依赖；
     `moon test` / `moon run` 两步就能复现。

2. **拆模块**，每个文件只干一件事：
   - `error.mbt` — `OrmError`（suberror）。
   - `value.mbt` — `Value` 枚举、`ToValue` trait、智能构造函数。
   - `ast.mbt` — `Column[T]`（幻影类型）、`Condition`、`Order`、`Assignment`。
   - `query.mbt` — `Select`/`Insert`/`Update`/`Delete` 构建器、`Statement`。
   - `conn.mbt` — `Row`、`ExecResult`、`Connection` trait。
   - `memory.mbt` — 内存后端的 `Connection` 实现。

3. **实现顺序**：先 value/error，再 ast，再 query，再 conn，最后 memory。
   每写一层就 `moon check` 一次，不等全写完才编译。

4. **测试**：先写 SQL 渲染的白盒测试（把 SQL 文本和参数顺序钉死），再写内存
   后端的 CRUD 测试，最后加一个黑盒冒烟测试验证外部消费。共 21 个用例。

5. **接口检查**：`moon info` 生成 `.mbti`，逐条核对公共接口，确认没有把内部
   字段漏出去。

## 踩过的坑（这些是真实记录，不是补写的）

- `and` / `or` / `not` 是 MoonBit 关键字，自由函数写不了，改成 `and_` / `or_`
  / `not_` 方法挂在 `Condition` 上。
- 自己起名 `enum Error` 撞了内置 `Error`，改 `OrmError` 并且用 `suberror`
  而不是 `enum`，否则 raise 不了。
- `pub enum` 的变体在包外是只读的（能 match 不能构造）。core 的 `Json` 用智能
  构造函数绕开，我也照做：`Value::int(1)`、`Value::text("x")`。
- trait 方法声明里接收者要写 `Self` 而不是 `self`（impl 里才用 `self`）。
- `!Err` 是废弃语法，签名写成 `raise OrmError`。
- `not(x)` 废弃，用 `!x`；`.is_none()` 废弃，用 `x is None`。
- `#warnings("-unused_type_variable")` 必须紧贴声明，中间隔 doc comment 会
  直接解析失败。

## AI 工具的使用方式

这次开发 AI 参与得很重，但方式是「工程负责人 + 工具」，不是「AI 一把梭」：

- 我（人）定目标、拆模块、定接口边界——`Connection` 要作为可替换边界、值必须
  走参数化、内存后端不解析 SQL 直接算结构化查询，这几个决策是我拍板的。
- AI 负责查资料和写代码：读 core 源码确认测试惯用法（`try!` 解包、
  `try/catch` 断言抛错）、确认 trait 的 `Self` 写法、确认 `#warnings` 的位置。
- 每一处改动都跑 `moon check` / `moon test`，编译不过就对着报错查 core 源码
  修正，不靠猜。上面「踩过的坑」就是这一轮轮编译报错堆出来的。
- 写出来的东西全部有测试兜底：SQL 文本、参数顺序、内存 CRUD、错误分支都断言。

结论是：AI 省掉了查 API 和写样板的时间，但设计决策和正确性验证是人握着，
每一步都落在能复现的命令上。

## 查询能力扩展

内存后端跑通之后把查询面补齐：聚合（`COUNT` / `SUM` / `AVG` / `MIN` / `MAX`）、
`GROUP BY` / `HAVING`、以及 `INNER JOIN`。`Select` 里加了 `aggregate`、
`group_by`、`having`、`join` 几个字段，`build()` 对应拼出 SQL 片段；内存后端
同步实现了这些结构化查询（JOIN 用嵌套循环，分组用 `group_rows` 分桶，聚合在
桶内折叠）。JOIN 只做 INNER、每次一个，够覆盖「分组统计」和「跨表关联」两类
最常见的场景。

## SQLite 驱动与 native 目标

第二个后端做成真正的 SQLite 驱动，验证「实现 `Connection` 就能换后端」不是
空话——调用方代码一行不改。

- **卖掉系统依赖**：直接 vendor 了 SQLite 的 amalgamation（`sqlite3.c` +
  `sqlite3.h`，约 9.5MB），`moon.pkg` 里 `options("native-stub": ["stub.c",
  "sqlite3.c"])` 把它链接进来，装系统 sqlite3 这步就省了。
- **FFI 边界**：`ffi.mbt` 里 `priv type Sqlite3` / `priv type Sqlite3Stmt` 做
  不透明句柄，`#borrow` 标只读参数，`extern "C"` 对应 `stub.c` 的 C 封装。
  `sqlite.mbt` 的 `prepare_bound` 走 `prepare -> bind -> step`，值永远通过
  `sqlite3_bind_*` 位置绑定，不拼进 SQL 文本。
- **跨包实现 trait 的坎**：`pub trait Connection` 在包外是只读的，实现不了
  SQLite 后端。查文档后把 trait 改成 `pub(open) trait Connection` 才放开跨包
  impl，这是 MoonBit 接口规则里容易踩的一处。
- **工具链比语言更折腾**：本机没 C 编译器，装了 WinLibs（GCC 14 + mingw-w64）。
  两个环境坑——一是 runtime 的 `env.c` 用 `rand_s`，GCC 14 当隐式声明硬报错，
  得在 `<stdlib.h>` 之前定义 `_CRT_RAND_S`；二是 `E:\9月黑客松\moonorm` 这个
  非 ASCII 路径被 MinGW 按 GBK 码页转坏，`.obj` 名变成乱码。解法：编译时拷
  一份 ASCII 路径副本 + 给 gcc 包一层注入 `-D_CRT_RAND_S` 的 wrapper。都是
  环境问题，不是语言问题。
- **结果**：`moon test --target native` 下 2 个 SQLite 白盒用例通过（CRUD 回环、
  null/float 绑定 + 原地 update）。

## LEFT/RIGHT JOIN、事务，与「可替换边界」的演示

这一轮把两件事补上：JOIN 的 LEFT/RIGHT 变体，和事务。核心思路还是那句
「实现 trait 就能换后端」——能力做成可选 trait，后端按自己有的能力认领。

- **JOIN 变体**：`Join` 加了 `kind`（`JoinKind::{Inner, Left, Right}`），
  `Select` 多了 `left_join` / `right_join`（`join` 仍是 INNER）。`build()` 拼出
  `LEFT JOIN` / `RIGHT JOIN`。这里是「接口先行」：SQL 渲染和 SQLite 端已经通
  （SQLite 原生支持 LEFT/RIGHT JOIN），内存后端这一轮只留占位——遇到 LEFT/RIGHT
  直接 `OrmError::Backend` 明确报「不支持」，不静默算错。
- **事务**：单独一个 `pub(open) trait Transactional { begin / commit / rollback }`，
  不塞进 `Connection`——内存后端是单语句存储，没有多语句事务这回事，就不实现
  这个 trait。`Sqlite` 实现了（`BEGIN` / `COMMIT` / `ROLLBACK` 走 `exec`）。
  能力是 opt-in 的，`Connection` 始终是那个最窄的共同边界。
- **演示**：`cmd/sqlite_demo` 跟 `cmd/main` 一模一样地拼查询，只是后端从
  `Memory` 换成 `Sqlite`，另加两处真实 SQL 后端才有的差异——`exec` 建表、事务
  包裹批量插入。两个 demo 并排就是「可替换边界」的活证据：换后端，调用方
  代码一行不改。

这一轮本机没有 C 编译器，SQLite 侧只保证 `moon check --target native` 通过、
native 测试不跑；wasm-gc 上新增的 JOIN 渲染和「内存后端拒绝 LEFT JOIN」用例
是实测通过的。

## 内存后端真求值 LEFT/RIGHT/FULL JOIN

上一轮 LEFT/RIGHT 在内存后端是「占位拒绝」，这一轮把它做成真求值，顺手把
`FULL JOIN` 也补上（SQLite 原生就支持，之前只是 DSL 没暴露）。

- **TDD**：先写用例再实现。`memory_wbtest.mbt` 加 3 个——LEFT 保留无匹配的
  左行、RIGHT 保留无匹配的右行、FULL 两边都保留，缺的一侧列填 `Value::Null`；
  `query_wbtest.mbt` 加一个 `full_join` 渲染用例，把 `FULL JOIN` 关键字钉死。
  写完这些用例是红的：`full_join` 还不存在，内存后端还在拒绝 LEFT/RIGHT。
- **实现**：`JoinKind` 加 `Full`；`Select::full_join` 和 `render_join_kind`
  的 `FULL` 分支照 LEFT/RIGHT 的套路补齐。内存后端 `join_rows` 从「只出匹配对」
  改成嵌套循环先算 `left_matched` / `right_matched` 两个布尔标记，再按 `kind`
  决定补哪些未匹配行、缺侧用 `null_row` 填。结果顺序固定：先匹配对、再左未
  匹配、再右未匹配，保证可断言。
- **结果**：wasm-gc 上 36 个用例全过（`Total tests: 36, passed: 36`）；SQLite
  侧 `moon check --target native` 通过。四个 JOIN 变体在内存后端全部真求值，
  不再是占位。

## 非相关子查询（IN / EXISTS）

把「子查询」这块从「没做」里划掉一部分：先做最常见的两种——`col IN (SELECT ...)`
和 `EXISTS (SELECT ...)`，`NOT` 复用已有 `not_()`。范围钉死在非相关（子查询不
引用外层行）；相关子查询和标量子查询仍是下一步。

- **TDD**：先写 5 个用例（3 渲染 + 2 内存求值）。渲染用例钉死 `IN (SELECT ...)`
  和 `EXISTS (...)` 的 SQL 文本与参数顺序；内存用例验证 `IN` 子查询按子查询结果
  过滤、`EXISTS` 子查询起全局门控（有命中 / 无命中两个方向）。写完是红的——
  `in_select` / `exists` 还不存在。
- **实现**：`Condition` 加 `InSelect(ColumnRef, Select)` / `Exists(Select)` 两个
  变体；`Select` 和 `Join` 补 `derive(Eq, Debug)`（`Condition` 现在引用 `Select`，
  得让 `Select` 可比较、可打印）。`render_condition` 及其上游 `render_where` /
  `render_having` / `render_join` 变成 `raise OrmError`——子查询要 `build()` 取
  SQL，而 `build()` 会校验表名。内存后端 `eval_condition` 加 `mem` 参数并变成
  raise，`IN` 子查询先跑一遍 `mem_select(sub)` 取首列做成员判断、`EXISTS` 判空；
  因为闭包不能 raise，把 `mem_select` / `mem_update` / `mem_delete` 里的
  `.filter` / `.map` 换成了手动循环。
- **结果**：wasm-gc 上 41 个用例全过（`Total tests: 41, passed: 41`）；SQLite 侧
  `moon check --target native` 通过。非相关子查询在内存后端真求值，不是占位。

## 标量与相关子查询

把子查询这块补齐到能覆盖「经典 SQL」那几道题：标量子查询（`col > (SELECT AVG(...))`
这类）和相关子查询（子查询引用外层行）。

- **标量子查询，TDD 先行**：`Column` 加 `eq_sub` / `ne_sub` / `gt_sub` / `gte_sub` /
  `lt_sub` / `lte_sub`，落到 `Condition::CompareSub(ColumnRef, CompareOp, Select)`。
  先写渲染用例钉死 `col > (SELECT ...)` 的 SQL 文本，再写内存求值用例——标量
  取子查询结果首行首列跟外层列比较，子查询空集时比较为 false。跑红后实现，其中
  撞上一个真 bug：`age.gt_sub(Select::from("users").avg(age))` 里 `AVG` 返回
  `Float`、列是 `Int`，跨类型比较落进 `_ => None` 永远 false。补了 `try_compare`
  的 `Int`/`Float` 双向分支（都提升到 Double）才过——这正是标量子查询最经典的
  用法，不能算边角。
- **相关子查询，真正的设计改动**：子查询要能引用外层行，就得把「外层行上下文」
  传进求值器。给 `mem_select` / `matches` / `eval_condition` 加了一个 `outer`
  帧（外层列的 `columns` + 当前外层 `row`），子查询分支把 `Some((columns, row))`
  透传给嵌套的 `mem_select`；`And`/`Or`/`Not` 递归时把帧继续往下带。这里最险的
  是**遮蔽问题**：原来列解析的非限定名回退会让内层表的同名列盖掉外层引用——
  `orders.id` 会把 `users.id` 遮住，子查询永远匹配不上。修法是引入表感知的
  `resolve_in_scope`：限定名先匹配；非限定名只有当 `col.table` 在当前作用域表列
  表里才回退，否则落到 `outer`。测试专门覆盖了这个边界——`users.id` 必须解析到
  外层 1，而不是内层 `orders.id` 的 100。相关 EXISTS / NOT EXISTS / 标量三种形态
  各一个用例，外加一个渲染钉死外层列出现在子查询里的 SQL。
- **结果**：wasm-gc 上 48 个用例全过（`Total tests: 48, passed: 48`）；SQLite 侧
  `moon check --target native` 通过，native 白盒 3 个用例也跑绿（`moon test
  ./sqlite --target native`）。相关层级钉死为单层：子查询只认自己的直接外层，
  不再往上追（grand-outer），这点写进 README 的 Limits。

## 现状与下一步

现在能做的：类型安全地拼 SELECT/INSERT/UPDATE/DELETE；聚合 + `GROUP BY` /
`HAVING`；`INNER` / `LEFT` / `RIGHT` / `FULL JOIN`（内存后端四种都真求值，缺侧
填 null）；子查询 `IN` / `EXISTS` / 标量比较，支持相关子查询（单层）；参数化防
注入；内存和 SQLite 两个后端走同一个 `Connection` 边界，换后端调用方代码不改；
事务走可选 `Transactional` trait（SQLite 有、内存无）。wasm-gc 上 48 个用例零
依赖可复现；SQLite 子包另有 3 个 native 用例（含事务）。

明确没做的：Postgres 等其它驱动。这些是自然的下下一步——驱动只要在实现
`Connection` / `Transactional` 时调 `build()` 拿 SQL 再绑定参数就行，SQLite 这
条路径已经趟通了。
